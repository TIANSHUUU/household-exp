# 食材词表种子设计

2026-08-03

## 要解决什么

网页上手动录食谱时，词表里没有的食材会被原样建成新 canonical（[assets/recipe.js:855](../../../assets/recipe.js)）：

```js
vocabInsert(unknown.map(k => ({ canonical: k, aliases: [], staple: false })))
```

所以录过「番茄」之后再输「西红柿」，会得到两条互不相干的词条。后果不是显示错乱，而是**冰箱匹配对不上**——同一样东西算成两样，`matchRecipes` 就会说你缺料。

原计划是给 Edge Function 加一个 `normalize` action：录入时遇到新词让 LLM 判断「这是不是已有的某个」，用户确认才写入。

## 为什么改成补词表而不是加 `normalize`

`normalize` 能兜住任何生僻词，但代价不小：

- 每次保存新食材要占一次配额，而免费档只有 **20 次/天**，还和用户自己在 AI Studio 的用量共享
- 多一步确认弹窗
- LLM 判断错了会静默污染匹配键——「生抽/老抽」「青椒/彩椒」这种它很容易合并掉，而这类错误极难发现

补一份带同义词的底表则是纯数据改动：零配额、零代码、零运行时风险，而且能覆盖日常做饭的绝大多数食材。**先补表，观察一阵，真撞到漏网的词再考虑 `normalize`。**

顺带一提：md 录入那条路（Claude 直接读文件上传）本来就会顺手补别名，所以 `normalize` 只对「手机上临时手打」这一个场景有价值，性价比更低了。

## 词表

145 条，其中现有 25 条 + 新增 120 条。范围按用户实际菜路定：中式家常 + 西式烘焙和早餐（购物清单里有希腊酸奶、蚝油、burrata、黑蒜酱、沙丁鱼，Bill 松饼是西式烘焙）。

每条形如：

```
番茄  ← 西红柿, tomato, tomatoes
土豆  ← 马铃薯, 洋芋, potato, potatoes
```

**英文别名统一补齐。** 原来覆盖得很不均匀——`全麦面粉` 有 `whole wheat flour`，但 `盐`、`糖`、`葱`、`香醋`、`料酒` 一个英文名都没有，`老抽` 的别名数组是空的。英文搜索完全依赖这些别名命中（见 HANDOFF 第三节），所以切到英文界面搜 `salt`、`sugar` 原本是搜不到的。

## 交付方式

`supabase/seed-ingredient-vocab.sql`，用户在 Supabase SQL Editor 里跑。

`on conflict (canonical) do update` 使它可重复执行——跑几遍结果一样。以后想加词就改这个文件重跑，不需要写迁移。

## 三条必须守住的约束

1. **canonical 永远是中文。** 它是匹配和搜索的机器键（HANDOFF 第三节铁律）。
2. **现有 25 条的 `staple` 原样保留。** staple 标错会让冰箱匹配失去意义：标多了什么都算你有，标少了每道菜都提示缺一堆。
3. **同一个词不能同时是两个 canonical 的键。** `buildAliasMap` 用 `Map.set`，撞了会**静默覆盖**，症状是搜索和匹配莫名其妙认错食材——不主动检查根本发现不了。

生成器对这三条都做了断言，任一不过就拒绝出 SQL。

## 新增的 staple 判断

新增 120 条里只有 2 条标了 `staple = true`：**米** 和 **鸡精**。其余全是 `false`。

这两条是判断题不是事实题，需要用户确认：家里是不是总有米、做饭放不放鸡精/味精。标错的后果是冰箱匹配把它们默认当「你有」。

## 怎么验证

`scripts/verify-vocab.py`：拉线上词表 → 按 `recipe.js` 同样的规则重建查找表 → 检查冲突 → 跑几组已知断言（西红柿→番茄、tomato→番茄、buttermilk→酪乳、salt→盐）。

这个脚本长期有用：**网页手动录入随时可能引入新的冲突词条**，种子表只是把起点垫高了，没法阻止以后再出问题。

人工再确认一项：网页上输「西红柿」，自动补全应该提示成「番茄」。

## 不做的事

- 不动已有食谱的 `ingredient_keys`。现在只有 Bill 松饼一条，脚本会核对；真有不一致再单独处理。
- 不加 `normalize` action。降级到「以后再说」。
- 不做词表管理界面。改词表 = 改这个 SQL 文件重跑，够用了。
