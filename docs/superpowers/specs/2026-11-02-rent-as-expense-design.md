# 租金改成每月自动记账，取消归档

2026-11-02

## 要解决什么

### 真实的 bug：租金按「账期」算，不按「月」算

`calc()`（[index.html:930](../../../index.html)）里租金是一个公式项，**每个活跃账期只加一次**：

```js
transfer = carryover + cfg.myRent - shared / 2 - pp + cp
```

账期跑多久都只算一笔。当前账期 `id=5` 从 2026-08-24 起一直没归档，到 2026-11-02 已经 70 天 ≈ 2.3 个月，区间内经过 **2 个租金日**（09-22、10-22），但公式只加了 1 × $1,250。

实测对账：

```
现在：transfer = -6984.63 + 1250 - 567.61 - 274.63 + 1109.96 = -5466.91
      → 页面显示「宝宝欠你 $5,466.91」✓ 和线上一致

应该：transfer = -6984.63 - 567.61 - 274.63 + (1109.96 + 1250×2) = -4216.91
      → 「宝宝欠你 $4,216.91」

差额 $1,250.00
```

**页面把宝宝的欠款多算了 $1,250。** 方向容易搞反，记清楚：租金是**你欠宝宝**的，少记一期 → 宝宝欠你的显得更多。

而且这个误差**每个月增长 $1,250**，只要不归档就一直涨。

### 更根本的：产品定位变了

原设计假设「每月租金日结清一次」，所以归档 = 结算 + 清零 + 滚存。用户 2026-11-02 说明实际用法完全不同：

> 目前我伴侣的欠款已经是租金的好几倍，我也不急着每个月结清。这个账单目前是**应收账款**的概念，而不是现收现付。

也就是说「归档」这个动作在真实使用里**从来没有对应的现实事件**——没有人在租金日转账。它只是为了让租金进账而不得不点的一个仪式，而用户不点，于是租金就不进账。

**把一个没有现实对应物的操作作为关键计算的触发器，是这个 bug 的根因。** 加个日期选择框去改进归档只会让它更精致，不会让它更对。

### 顺带暴露的旧问题：开支归期按录入时间

[index.html:1097](../../../index.html)：

```js
await dbInsert({ id: newId, ...row, cycle_id: activeCycle ? activeCycle.id : null });
```

开支在录入那一刻被盖上「当前活跃账期」的章，和它自己的 `date` 无关。用户出门旅行回来统一补录时，账就进错期。

实测历史数据里已经发生过 3 笔（164 笔中）：

```
id=3「7月账期」区间 2026-07-25 → 2026-08-24，但含有
    07-23  ovo energy   $70.00
    07-24  中医          $161.39
    07-24  猫盆          $10.00
```

这三笔日期属于 6月账期（那期 07-25 结束），因为是归档后补录的，被记进了下一期。**$241.39 结算错了期。**

本方案取消归档之后，「开支属于哪个账期」这个问题自然消失——只剩一个永远活跃的账期，录入时间和开支日期都不再影响归属。所以这个旧问题**不需要单独修**，但历史那 3 笔也**不回头改**（见「不做的事」）。

## 设计

### 1. 租金变成一条真实开支

| 字段 | 值 |
|---|---|
| `type` | `partner_paid`（宝宝替我垫付） |
| `date` | 每月租金日 |
| `amount` | 生成那一刻的租金金额 |
| `description` | `房租` |
| `cycle_id` | 当前活跃账期 |
| `id` | **`YYYYMMDD` 整数**，如 `20260922` |

`type` 选 `partner_paid` 是因为符号方向正确：`calc()` 里 `+cp`，租金是你欠宝宝的，要让 `transfer` 变大。

### 2. id 用日期，幂等就白送了

现有 id 只有两种来源：`Date.now()` 的 13 位毫秒戳（如 `1793592786771`）和种子数据的 1–19。8 位的 `YYYYMMDD` 和两者都不会撞。

好处是**不需要任何「补到哪了」的状态记录**：重复插入直接违反主键约束而失败，捕获并忽略即可。两台设备同时打开也只会成功一个。

这一点很重要，因为 `cfg` 存在 localStorage（[index.html:924](../../../index.html)），**是每台设备各一份的**——任何依赖本地水位线的方案在多设备下都会重复补登。

### 3. `calc()` 去掉 `myRent` 项

```js
// 之前
transfer = carryover + cfg.myRent - shared / 2 - pp + cp
// 之后
transfer = carryover - shared / 2 - pp + cp
```

不去掉就是双重计算。`renderArchived()`（[index.html:1246](../../../index.html)）里还原历史账期的那段**不改**——历史账期当时确实是按公式算的，改了明细就和结算额对不上。

### 4. 补登时机：页面加载时

**扫描区间的起点是 `max(已存在的最后一笔房租行的日期, 活跃账期 start_date)`，且严格大于它**；终点是今天。区间内每个租金日检查一次，缺的补上。

三个边界都必须按这条处理，少一条就会多记或少记一个月的租金：

1. **起点严格大于 `start_date`。** `start_date` 当天及以前属于上一期的结算范围（当前账期 `start_date = 2026-08-24`，上一期 `id=3` 的 `end_date` 也是 `2026-08-24`）。如果某个租金日正好落在 `start_date` 当天，算进来就是和上一期重复计。

2. **起点要看最后一笔已存在的房租行，不能只看 `start_date`。** 否则改租金日会出事：假设以后把租金日从 22 改成 25，补登会去扫每月 25 号，而 9 月 22 号那笔已经存在——同一个月记两次租金。以已有的最后一笔房租为水位线就不会。

   注意这个水位线**存在数据库里**（就是房租行本身），不是 localStorage。[index.html:924](../../../index.html) 的 `cfg` 是每台设备各一份的，任何本地水位线在多设备下都会失效。

3. **租金日设成 29/30/31 而某月没有该日** → 用那个月的最后一天。

### 4.5 房租行不能删，但能改金额

删掉之后下次加载会发现对应 id 不存在，于是又补回来——一行删不掉的鬼行。所以：

- 房租行**不显示删除按钮**
- **允许编辑金额**（记错了要能改）。编辑保留原 id，所以不会触发补登。

如果真要去掉某个月的房租，去 Supabase 控制台删，或者把金额改成 0。这个取舍写进设置面板的说明文字里。

### 5. 租金金额和租金日搬进数据库

**这是必须的，不是顺手优化。** 租金从「显示用的公式参数」变成「写进数据库的真实金额」之后，两台设备各存一份就会出事：同一个月的租金记成多少，取决于谁先打开网页，而且因为 id 幂等，先写的那个值会永久固定下来。

用户需要在控制台跑：

```sql
alter table public.cycles
  add column if not exists rent_amount numeric,
  add column if not exists rent_day    integer;
```

存在活跃账期那一行上。设置面板改成读写数据库。

**改了只影响以后生成的行**，已生成的行保留当时金额——这正是用户要的「过几个月租金会涨」。

### 6. 归档按钮删掉

移除 `newCycle()`（[index.html:1166](../../../index.html)）和设置面板里的「账期」那一块。往期记录抽屉保留为**只读历史**，当前账期永远 `active`，`carryover` 永久停在 `-6984.63`。

| | 之前 | 之后 |
|---|---|---|
| 宝宝欠款 | $5,466.91 | **$4,216.91** |
| 新增开支行 | — | 2 笔（`20260922`、`20261022`），各 $1,250 |
| 历史账期 | 不动 | 不动 |
| `carryover` | -6984.63 | -6984.63（不再变化） |

## 不做的事

- **历史三期不重算。** 那三期当时按「一期一笔租金」结算，且钱已经按那个数字转过。重算会造出新的错，而不是修掉旧的错。
- **cycle 3 里那 3 笔错期的开支不动。** 同上，$241.39 已经结算过了。
- **开支列表变长的问题这次不处理。** 不再归档意味着主页一直堆，当前 26 笔，按每月约 15–20 笔估算一年后约 250 笔。需要按月折叠或分页，属于独立改动，已记入 HANDOFF 第八节待办。

## 怎么验证

仓库没有测试框架，PURE LOGIC 段的断言是唯一能自动验的部分。

1. **给 `scripts/verify-fx-logic.js` 同款的纯函数断言**：租金日期序列生成（含 31 号落在 2 月、跨年）、`calc()` 去掉 `myRent` 后的结果。按仓库惯例，**断言先让它失败一次再改对**。
2. **幂等性**：连续调用补登两次，第二次必须零插入。
3. **水位线**：造一个「已有 09-22 房租行、然后把租金日改成 25」的场景，补登必须**不**在 9 月再插一笔。
4. **线上实跑**：跑完 SQL 和部署后，确认页面显示 $4,216.91，且两笔房租出现在列表里。
5. CLAUDE.md 规定的五个检查全过。
